# 长文分析分步生成与续写

日期：2026-10-21（北京时间）

原流程先分段阅读长文，再请求模型一次生成全部实现与验收内容。单次输出到达上限后直接报错，先前生成的正文不保留；生成前的范围检查还固定限制为 1024 Token，推理模型可能在检查时便耗尽额度。

现在按以下步骤处理：

1. 原文按约 6000 字符逐段读取，每段提取功能、原文依据、依赖与待确认问题。
2. 本机分配固定 F 编号；完全同名功能合并，保留每一段原始证据。
3. 按功能分别生成 S 实现步骤与 AC 验收标准，检查编号连续、验收项关联与实现步骤覆盖。范围约束随当前功能一起提供。
4. HTML 原型的流程、交互、错误恢复和测试方向各自分段生成。
5. 本机组装完整 Markdown；完整报告不再作为后续请求的历史正文反复回传。

Chat Completions 的 `finish_reason=length` 和 Responses 的 `incomplete_details.reason=max_output_tokens` 可以触发正文续写。请求仅携带当前任务、最多 3000 字符的已写正文末尾和衔接锚点；验证锚点后再拼接，保留 Markdown 边界。其他中断原因、拒答、重复输出和无法衔接的内容不作为成功结果。

每次请求设置 48000 字符的保守输入边界，仍使用用户配置的单次输出 Token 上限。字符预算不等于供应商 Token 计数，不声称支持所有上下文大小的模型。每个步骤每次运行最多 12 次生成请求，超出时保存进度供用户继续；单步异常增长也会明确停止。请求拆分会增加调用次数，实际耗时与费用取决于模型、需求规模和输出设置。

草稿与成功报告分开存放于本机 SQLite。每步及每次已收到的截断正文写入草稿，不存储 API Key；失败或取消不覆盖成功报告。草稿随数据库备份迁移，删除文档时级联清理。原文改变会清除旧草稿；配置与补充要求指纹不匹配时新建草稿。输出额度和超时可以调整后继续。最终报告保存与草稿清理在同一事务中完成。

验证使用本机模拟服务与临时数据库，覆盖两种协议的 JSON/Markdown 截断、空正文推理耗尽、衔接失败、请求次数边界、取消恢复、重启恢复、输出额度调整、配置变更失效、数据库迁移、失败保存回滚及已有报告保留。真实模型的需求理解质量和不同服务商的续写遵循情况仍需实际生成后核对。

接口依据：[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。上下文容量约束输入和生成内容的总量，`max_tokens` 约束单次生成；扩大上下文容量不能代替分步生成和输出恢复。

## DeepSeek 空正文与校验纠错

真实联调发现 `deepseek-flash` 默认高强度思考可能在 4096 Token 内耗尽额度而不返回正文。对 DeepSeek 官方地址上的 Flash、V4 Pro，文档分析与连接测试明确使用非思考模式；Chat Completions 映射 `thinking.type=disabled`，Responses 映射 `reasoning.effort=none`。保持用户保存的输出额度，其他服务与普通对话不强制切换。依据见 [DeepSeek 思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)。

模型自行添加的小标题降至功能标题之下，代码围栏内的内容不变。结构或编号校验失败时，保留已完成步骤，只将当前不合格步骤连同具体错误重新请求，最多自动纠正两次，并计入单步 12 次请求上限。错误反馈随草稿保存；拒答、超时、服务错误不适用此重写机制。验收关联检查同时拒绝引用未提供的其他功能步骤。

本机真实文档联调使用原有 4K 额度，成功读取两段原文、拆出 47 个功能，并完成前 18 个功能及第 19 个功能的实现步骤；长步骤和验收的截断续写均已实际衔接成功。第 19 个功能验收校验失败后，已完成内容保留。随后加入有界纠错与恢复测试；Mac 锁定，完整报告与新纠错流程的真实模型联调尚待解锁后继续，不能将这次部分生成记为完整成功。

## 逐段预览与生成中补充要求

解锁后的真实联调继续到第 38 个功能；第 23 个功能缺少 S-023-07 关联时，自动修正后通过。第 38 个功能因续写锚点未能衔接而停止，检查点已保存 79 段可读内容。新增草稿读取接口直接从旧、新检查点还原可读的范围、功能、步骤和验收，不需要重新调用模型；进度通知只携带版本号，页面单独读取草稿，避免每段生成都重新传输带图片的完整原文预览。

草稿按功能选择阅读，默认跟随最新生成部分，手动选择后保持阅读位置；可以复制全部已生成内容。片段明确标为已生成、未完成或待修正，完整报告与过程草稿分开保存和展示。续写无法衔接或重复锚点时，不拼接未验证的新内容，改为有界重写当前段。

补充要求输入框不再随生成禁用；应用新要求会取消并等待旧请求结束，再启动新版任务，上一版内容保留并标为待更新。后台新版任务继续持有存储与工程操作锁，取消或关闭时不会被等待中的修订请求重新启动。草稿读取与修订接口沿用主框架来源检查和工程归属校验。

自动测试覆盖部分内容在失败与重启后仍可读、进度提前通知、旧版与新版分离、生成中修订取消旧请求、无效补充要求不打断任务，以及修订后仍阻止数据迁移与工程清理。

实际桌面验证：原有检查点直接展示，随后可读内容增加到 96 段；生成中输入补充要求会出现应用按钮，测试文字未提交并已清除。切换至 F-001 阅读时，“跟随生成”关闭，后台仍推进后续功能。完整报告尚未完成，部分草稿已可读取、复制与继续。前端类型、格式、158 项测试及构建通过。

## 通用下拉与最新内容导航

全局 `Select` 统一分析草稿、分析范围、模型设置、测试任务和历史版本的单选交互。触发器使用紧凑高度、单层焦点样式和主题色；弹层支持长名称、列表滚动、已选项定位、窗口边缘翻转、禁用项和键盘选择。弹窗中的列表归入弹窗的无障碍结构，Esc 先关闭列表，Tab 继续正常移动焦点。

“跟随生成”拆为「查看最新内容」和「新内容生成时自动切换」。前者返回当前版本的最新功能并定位最新段落，后者在生成期间控制自动切换；手动选择功能会取消自动切换。

macOS 本地启动会在桌面应用的 `node_modules/.cache/desktop-runtime` 中准备独立的「序舟.app」外壳，再使用该外壳启动，避免系统菜单仍显示 Electron。共享 Electron 依赖、Bundle ID、`app.setName` 和已有数据目录保持原身份，Windows 启动路径不变。安装包继续使用已有 `build.productName`，本次没有生成安装包。macOS 系统名称取自应用包信息，依据见 [Electron 应用分发说明](https://www.electronjs.org/docs/latest/tutorial/application-distribution)。

重启后系统菜单已实际显示「序舟」，原工程、96 段草稿及已保存设置仍在。已检查浅色与深色下拉外观、长列表定位、键盘切换、禁用项跳过、弹窗内 Esc/Tab 行为。前端类型、格式、168 项测试和构建通过。
