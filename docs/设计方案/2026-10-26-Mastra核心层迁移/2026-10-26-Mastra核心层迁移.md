# Mastra 核心层迁移

日期：2026-10-26（北京时间）。

## 运行架构

桌面主进程使用 `@mastra/core` 1.79.0 和 Zod 4.4.3，作为进程内库运行。React 通过现有 preload / IPC 调用业务服务，业务服务进入 Mastra Workflow，由 Agent 完成模型请求、Tool 调用已有执行器。首次 AI 或测试执行操作才动态加载框架。

```text
React UI → 受限 preload / IPC → Workspace / Testing / Terminal 服务
                                      ↓
                              Mastra Workflow
                           ↙                     ↘
                 Mastra Agent                 Mastra Tool
                      ↓                            ↓
              用户模型协议适配器             工程命令 / 内置浏览器
                      ↓                            ↓
           用户配置的模型服务              原有范围检查与执行记录

业务资料、历史消息、生成检查点 → 原有本机 SQLite
```

无需启动 Mastra HTTP 服务、Studio、Python 或容器。现有启动命令仍为 `cd frontend && pnpm dev:desktop`；本地构建运行仍为 `pnpm desktop`。

## 核心模块

| 模块 | 职责 |
| --- | --- |
| `frontend/apps/desktop/src/mastra/runtime.mjs` | 延迟加载入口、工作流与工具调用接口、取消信息转换、关闭框架遥测 |
| `frontend/apps/desktop/src/mastra/engine.mjs` | 注册 Agent、Workflow、Tool；隔离每次调用的 RequestContext；释放完成任务 |
| `frontend/apps/desktop/src/mastra/model-provider.mjs` | 实现 Mastra 支持的 LanguageModelV2，适配现有模型配置和接口协议 |
| `frontend/apps/desktop/src/model-client.mjs` | 保留业务使用的 `complete` / `completePart` 契约，统一进入 Mastra Agent |
| `frontend/apps/desktop/src/analysis-text.mjs` | 提供业务续写、锚点拼接和校验修正规则，由 Workflow 控制循环 |

注册的 Agent 分别负责工程讨论、需求分析、测试设计、网页计划、范围审查和连接检查。提示词与模型配置按请求传入，不在共享 Agent 上修改配置，也不从环境变量补读 API Key。

## 工作流

| 工作流 | 执行阶段 |
| --- | --- |
| `document-analysis` | 审查分析范围 → 生成功能实现与验收报告 |
| `chat-answer` | 审查本轮请求 → 生成回答 → 审查候选回答；请求被拒绝时提前结束 |
| `chat-turn` | 获取回答 → 提交并等待工程命令 → 基于真实结果总结 |
| `test-document` | 审查范围 → 整理资料 → 生成各段测试文档 → 合并校验 |
| `browser-plan` | 读取页面 → 逐用例编写计划 → 校验全部计划 |
| `browser-execution` | 使用 `foreach` 且并发数为 1，顺序执行已审阅用例；首次失败后跳过后续自动执行 |
| `text-continuation` | 使用 `dountil` 控制正文续写及局部修正，完成或达到 12 轮后退出 |

功能拆分、编号分配、引用校验、资料分段、报告组装保留为业务函数。Workflow 管理执行顺序，避免把这些确定性规则交给模型自行决定。

## 工具与协议兼容

`project-command` 和 `browser-action` 是通过 `createTool` 定义的 Mastra 工具。命令仍经过 `TerminalService` 的工程范围、用户本轮请求、实际脚本和路径检查；网页操作仍使用用户审阅的执行计划、同源限制和操作白名单。生成计划不会自动开始测试。

工具由 Workflow 调度。为兼容现有模型服务，工程命令继续采用经过校验的 JSON 候选格式；本次没有要求供应商支持原生 function calling，也没有引入开放式自主命令循环。

模型协议适配器保留：

- 用户指定的 Base URL 和模型名称，不进行供应商自动路由。
- Chat Completions / Responses 两种接口，以及 `max_tokens` / `max_completion_tokens` 配置。
- 无密钥本机模型、超时、取消、响应大小限制、拒绝重定向和 Responses 的 `store: false`。
- DeepSeek 官方指定模型的关闭思考开关，仅在原有要求直接输出的任务中启用。
- 模型拒绝、异常结束、空正文和非 Token 原因的不完整输出均作为失败处理。

Agent 的单次生成限制为一步，模型传输及 Workflow 不自动重试。续写和校验修正仍遵守原有的有界规则，命令和网页操作不会因框架重试而重复执行。

界面继续使用原有逐字呈现方式。适配器读取完整 JSON 响应后交给 Mastra；本次不宣称实现供应商 SSE 流式传输，也不开放图片或原生工具消息输入。

## 本地数据与生命周期

文档、分析结果、聊天、测试任务、执行证据和生成检查点继续保存在现有 `test-agent.sqlite`。本次没有变更数据库 Schema、保存目录指针或系统凭据存储身份。原来的分段检查点格式与指纹算法保持兼容；未完成操作仍由业务层恢复，带外部副作用的命令不会在重启后自动重放。

Mastra 默认创建的内存存储仅供框架运行使用；不配置 Agent Memory，不持久化 Workflow 快照，不建立另一份磁盘数据库。每次执行完成后清理运行句柄及请求上下文。模型地址和密钥由设置服务在主进程解密，保留在当次请求的闭包中。

框架日志和使用情况遥测关闭，不配置远程追踪。可选的 `onRuntimeEvent` 仅返回固定的 Agent、Workflow、步骤或工具标识，不携带正文、命令参数或凭据；默认不输出或保存。

Mastra 可能先响应取消，再结束底层请求。因此适配器记录正在进行的请求，调用结束前等待实际传输收尾。关闭应用、清理工程或切换保存目录仍按原有互斥机制等待任务结束，防止请求晚到后再写入状态。

## 使用已配置模型联调

新增显式运行的真实模型检查，不加入普通 `pnpm test`：

```bash
cd frontend
pnpm --filter test-agent-desktop test:live --profile development
```

`development` 读取开发模式配置，`production` 读取本地构建运行模式配置。脚本使用应用自己的 Electron / safeStorage 解密已保存的模型密钥，模型地址、协议、输出额度和超时沿用现有设置。此命令会向所配置的模型服务发送独立样例并消耗其额度。

联调在系统临时目录建立独立 SQLite 和命令工程，读取原设置时使用只读连接，不复制用户文档或把密钥写入结果。检查包括连接、需求分析、带引用的对话、测试文档生成，以及通过对话实际提交成功/故意失败的 Node 测试命令。命令保留既有审查和执行器；“故意失败正确记录”是通过的检查，报告中的 `status` 与实际 `commandStatus` 分开保存。

完成后输出结果目录，其中 `result.json` 保存检查结论、真实 HTTP 状态、用量和命令输出，Markdown 文件保存模型正文。需要只重测生成时，可复用前次完整联调的分析，脚本先核对两次需求夹具一致：

```bash
pnpm --filter test-agent-desktop test:live --profile development --recheck-generation <前次联调结果目录>
```

测试文档生成会向后续分段提供已生成用例摘要，同名用例需修正后才能保存；不合并不同层级或前置条件的测试。短需求的完整原文在各组共享，防止局部分析把已确定规则改写为待确认。长需求不截取前文冒充全文，资料仅在当前组缺失时需明确说明局部边界。相关回归覆盖最大 100 条用例、4,000 字符范围与续写同时存在时的请求预算。
